# v1.5.1 实施计划：全信道解锁 + 每信道"各国最大值"功率上限（TX auto 省电）

日期：2026-11-05

## 机制确认（先讲清楚，决定实现路径）

1. 逐信道功率上限来自**监管数据库 regdb**，不是 WCNSS，也不是全局 txpower。
   - `iw phy set txpower fixed X` 是全局单值；若 self-managed PHY 接受，就是"一直按 X 发"，
     即满发耗电，不符合需求。
   - 监管表里是逐信道、逐国家的上限。"每信道取所有国家最大值"只能改这张表实现。
   - v1.5 的 WCNSS 注入 / 全局 fixed 功率都不覆盖逐信道上限，保留但不承担此目标。
2. 上限拉满 ≠ 一直满发。实际发射保持 `TX_POWER_MODE=auto`：驱动/功率管理自行决定，
   省电；上限只决定"允许到多高"。
3. 解锁所有频段/信道分两档：
   - 实用级（v1.5 现成）：单一最开放国家（US/CA），已含 6GHz + 320MHz + 宽信道。
   - 理想级（本次目标）：所有国家的所有信道 + 每信道各国最大值 => 必须生成自定义监管表。

## 诚实边界

未拉到设备 regdb.bin 且未真机验证前，不声称"已生成可用的全信道 regdb"。
本方向 100% 依赖设备：regdb 格式、驱动是否接受非官方表、重载后行为都需实测。

## 设备侧步骤（待用户授权连机后执行，MCP 走独立链路不断网）

- [ ] D1: 定位并拉取设备 regdb.bin（路径/大小/哈希），确认格式与版本
- [ ] D2: 遍历候选国家（至少 US/CA/CN/JP/EU 主要成员），`iw reg get` / `iw phy`
      采集"信道 x 国家"功率上限矩阵（2.4G / 5G / 6G 全信道）
- [ ] D3: 生成自定义 regdb：全信道 enabled，每信道上限 = 该信道在所有国家中的最大值；
      保留原表结构与校验（按 regdb 格式要求处理 CRC/版本字段）
- [ ] D4: bind-mount 自定义 regdb 重载驱动（FORCE_WIFI_TOGGLE 或重启验证），确认：
      全信道 enabled、逐信道上限为各国最大值、6GHz/320MHz 可用、驱动不 crash、
      实际 TX 为 auto 管理（连接后实测 txpower 回读与功耗表现）
- [ ] D5: 对比报告：原表 vs 自定义表的逐信道差异、6GHz 可用性、DFS 行为变化

## 模块默认集成（验证通过后）

- 自定义 regdb 作为模块默认 REGDB 源（保留"按国家选择"作为可选项）
- TX_POWER_MODE 默认 auto（省电），fixed 保留为手动旋钮
- 诊断导出增加"当前监管表来源 + 逐信道上限"一节，便于核对

## 依赖与风险

- regdb 若带驱动侧校验和/签名，需按格式要求重算，否则驱动可能拒绝或回退
- 全信道解锁后 DFS/AFC 行为随信道类别而定，室内/室外限制由使用环境负责
- 功耗：上限提高后个别信道在驱动功率管理激进时可能偏热/偏耗，用实测数据回看

## 2026-11-05 逆向实证结果（已确认，勿重做）

### 已破译的结构（r1=原版 / r2=小米版 / r3=kiwi 版，均 24278 字节）
- 索引区：偏移 4 起，每国 16 字节：
  `[u16 值A(频段计划id)][u8 b2][国家码NUL][国家码NUL][u16 0x0328 标签][u16 grp][u16 ptr][u8 flags]`
  原版 237 国，小米版 238 国（末尾加 "XA"，ptr=0xa100）。
- ptr/grp 不是文件偏移（大量值 > 文件长度），是固件加载后的虚拟地址/索引；
  频段数据池在文件 0x1000 之后，LE16 频率(MHz)，多国共享同一池。
- 逐信道功率上限就在池内（如 2.4G 30dBm=0x1e @0x203b，5G/6G 各 24=0x18）。
  "所有国家×所有信道"矩阵 = 解析此池 + 索引映射，不需要逐国切国家码采集。
- 小米版改动 = 32 国索引字段 + 池内 574 字节（1cce-5908 散布），且改池的国家
  其"值A"同步变化 —— 值A 是每国频段计划的内容标识，非独立校验。

### 文件头校验：已严格证伪纯软件可解（a2ce / 69e9 / 7d7b，后两字节 04 00 为版本）
已穷举排除（三份文件互验，非单样本过拟合）：
- 全 65536 多项式 × 正/反方向 × 全 init × 全 xorout × 连续区间作用域（差分线性法，GF(2)）
- 任意连续区间 [a,b) 的字节和 / 异或（前缀和+哈希全区间搜索，0 命中）
- 位置加权字节和、u16 字和、字段和（f01/b2/grp/ptr/fl）——三份文件无一致解
- 标准 CRC16 目录 43 种 × 8 作用域
差分命中过的候选（0x860f/0x75e1/0xa4c1/0xa6be/0xb553）经 r3 第三份文件判决全部为巧合。
结论：校验非任何"连续字节区间的线性/加权/求和类"算法；
大概率是固件侧 keyed digest（regdb 由 WCN 固件加载校验，host 无源码可读）。

### 真机 bind 实验（已还原，vendor md5 与备份一致）
- 实验1：头校验清零、内容不动 → 驱动拒载，回退最小域（phy 丢 6GHz）。
- 实验2：池内功率 30→40、头校验保留原值 → 固件不采纳（phy 仍 30dBm）。
- 两者合并：文件被整体内容校验，只改任一部分都过不了。

### 结论与决策点（等用户拍板）
1. "每信道取各国最大值"的自定义 regdb 路线：结构已破译、生成器可写，
   但**校验不可离线复算** → 该路线在本机停止，除非走固件侧分析或找到
   官方/社区已解包的同芯片 regdb 生成工具（有第三方来源即可直接比对验证）。
2. 现成可用、已验证、无风险的路（v1.5.0 已实现，默认 US）：
   强制最开放监管域（US：2.4G 30 / 5G 最高 30 / 6G 全开 + 320MHz），
   实际发射保持 TX auto（省电，不是满发）。这是"不锁地区、能力全开"的
   工程最优点，逐信道上限已是该硬件合规可达的最大值集合。
3. 若仍要逐信道绝对最大值：选项 = (a) 接受 US 上限（推荐，已达成）；
(b) 反编译 WCN 固件找校验（工作量大、需授权）；(c) 找同芯片第三方 regdb 工具。

## 2026-11-23 重大修正：布局模型与"校验"语义已被实测推翻重建

本节推翻上文 2026-11-05 的多条结论。触发点：后台网络调研找到第三方同芯片家族
项目 `rgnv/GhostUnlock-XQ-GE74`（Sony Xperia 1 VIII / 同 qca_cld3 peach 家族 /
同 24278 字节 / 同格式）。其 patcher 只改 1 字节（US 记录的 6G superdomain）
**完全不动前两字节**即真机 live-verified；其样本里前两字节恰为 `00 00`。
据此重做实测，逐条结论如下（全部有可复现命令与读回证据）。

### 修正 1：记录边界 —— 文件是从 offset 0 起的纯 16 字节记录流，没有 4 字节头
上文把 `[0:1][1:2]=a2ce` 当全局校验、`[2:3][3:4]=04 00` 当版本，是**错位解读**。
正确布局（6 份真档全部吻合，ISO 数字码逐一验证 AF=4、AX=248、AL=8、DZ=12…）：

```
每条 16 字节记录（offset 0,16,32,…,0xFF0）：
  [0:2]  u16 LE  逐记录 flags/保留（不是全局校验！）
  [2:4]  u16 LE  ISO 3166 数字国家码（AF=4, AX=248, US=840, CN=156, JP=392, XA=4100）
  [4:6]  u16 LE  reg_dmn_pair_id（对应 reg_db.h enum reg_domain）
  [6]    u8      6GHz super domain（enum reg_super_domain_6g）
  [7:10] alpha2 + NUL
  [10:13] alpha2 重复 + NUL
  [13:15] u16 LE 常量标签 0x0328（个别国家 0x0128/0x0228/0x0028）
  [15]   u8      tail flag（0x05=140 国 / 0x00=96 国 / 0x03=1 国）
```

实证：`od -An -tx1 -N48 r1.bin` → 第 0 条 `a2 ce|04 00|37 00|00|AF…`，
第 1 条 `00 00|f8 00|27 00|02|AX…`（AX 的 ISO=248=0xf8 ✓），
第 2 条 `00 00|08 00|7c 00|00|AL…`（AL=8 ✓）。
`[0:2]` 在多数记录里是 flags 位（实测非零样本：0x800、0x40、0x400，
AD=0x0800、BE=0x0040、XA=0x0400），只有第 0 条（AF）被厂商写成 `a2ce/69e9/7d7b`。
**"每档唯一变动的非零字段"这一差分观察仍然成立，但它是第 0 条记录的 flags 槽，
不是覆盖全文件的校验和。**

### 修正 2：真机实测证明该字段不是文件内容校验（推翻上文"实验1 清零被拒"）
同一方法（bind-mount 替换 + svc wifi disable/enable 重载）三个变体的实测读回：

| 变体 | `[0:2]` | 其余字节 | 真机结果（iw reg get / iw phy） |
| --- | --- | --- | --- |
| 原版 | `a2 ce` | 不动 | 基线：phy#0 US，102 条 MHz 行，含 6GHz |
| 改 `ff ff` | `ff ff` | 一字节未动 | **拒载**：无 phy#0，global 00 退化表，丢 6GHz |
| 改 `00 00` | `00 00` | 一字节未动 | **接受**：phy#0 US 完整，102 MHz 行，6GHz 在 |

结论：`0000` 是合法值（=默认/无 flags），`ffff` 非法。若是全文件内容校验，
`00 00` 与 `ffff` 应同样被拒。上文的"实验1 清零被拒"与本次 `00 00` 通过相矛盾，
推断当时另有变量（重载方式或挂载点状态），**该旧结论作废**。
→ 因此**不存在"校验不可离线复算"这一卡点**：改记录时把 `[0:2]` 写 0 即可。

### 修正 3：活体 iw 表来自 host 编译期内置表，不来自文件数据池
本平台同源 host 源码（LineageOS/android_kernel_xiaomi_sm8550-modules,
qca-wifi-host-cmn `umac/regulatory/core/src/reg_db.c`，"database version 41"）
**没有任何 regdb.bin 解析、CRC 或 checksum 代码**——它是一张编译期常量表：
`reg_rules_2g/5g/6g` + `regdomains_2g/5g/6g` + `g_reg_dmn_pairs[]` + `g_all_countries[]`。
对照实测逐条吻合：host `FCCA={CTL_FCC,…,CHAN_1_11_1}` 且 `CHAN_1_11_1={2402,2472,40,30,0}`
→ iw 显示 `(2402-2472 @40),(6,30)`；host `CHAN_5490_5730_1={5490,5730,160,24,RADAR}`
→ iw 显示 `(5490-5730 @160),(N/A,24),DFS`；`CHAN_5735_5835_2={…,30,0}` → `(N/A,30)`。

因此模型是：**iw 监管表 = host 内置规则库，按记录里的 pair/super6g 选择子渲染**。
实测旁证：把文件池里 2.4G 功率字节（0x203A，`1e`→`18`，即 30→24 dBm）改掉、
`[0:2]` 置 0，重载后 iw 仍是 30 dBm —— **文件数据池不参与 self-managed 路径的 iw 表**
（上文"改池 30→40 不生效"由此得到解释，不再是"整体内容校验失败"）。
这也解释了 GhostUnlock 为何只改 super6g 一字节就能让 6GHz 信道真机出现。

### 修正 4：选择子可对号入座，自定义表 = 挑选择子（离线可构造）
从 6 份真档 dump 的记录选择子（tools/regdb_work/recdump2.py）：

| 国家 | ISO | pair | super6g | host enum 对号 |
| --- | --- | --- | --- | --- |
| US | 840 | 234 | 0x21 | `FCC15_FCCA = 0xEA`（=234） |
| CN(r1/r3) | 156 | 116 | 0x00 | `APL14_CHNA = 0x74`（=116） |
| CN(r2 小米) | 156 | 142 | 0x00 | 0x8E，不在该版 enum（小米自建/新版） |
| JP | 392 | 225 | 0x16 | `MKK2_6G_16`（320MHz 版日本） |
| DE/TW | — | 39 / 233 | 0x02 | `ETSI1_6G_02` |
| XA(小米自建) | 4100 | 225 | 0x0f | 0x0f 不在该版 enum |

要点：① pair id 最大值 239、出现 52~54 个不同值，与 host `enum reg_domain` 的取值域一致；
② 0x21、0x0f、0x8E 超出我手上 reg_db.h 的枚举上界（0x18）——peach 固件/host 版本更新，
**说明厂商确实会自建/追加 pair 与 superdomain 值**（r2 的 CN=0x8E 与 XA 就是厂商追加的活证据）；
③ regdb 里**原本没有 "00" 记录**（`grep` 无 alpha2='00'），而 host 源码有
`#define REG_WORLD_ALPHA2 "00"`；④ 记录区 0xEE0 起有 **18 个全零空槽**（237 国止于 0xED0）。

### 修正 5：因此"自定义 00"路线重新变为可行，且卡在"选择子组合是否够用"
可行部分（离线可做 + 已有 live-verified 先例）：
- 新增/改写 `00` 记录：ISO=0、alpha2='00'、`[0:2]=0`，pair 填 234（=US）→
  预期 00 域直接等于 US（2.4G 30dBm、5G UNII-1/2/3 全开、6G 全开 + 320MHz）。
- super6g 填 0x03/0x21 之类厂商已在用的值（GhostUnlock 实测：0x18 会让固件崩，
  0x03 稳定）→ **必须挑本机/同固件已出现过的值，别造新值**。

## 2026-11-23 晚间终局：选择子模型被真机否证，"自定义 00 记录"路线关闭

本节作废上文"修正 5"提出的两条未闭环实验（pair 交换、新增 00 记录）及其
"自定义 00 重新可行"的结论。三条新证据全部有可复现脚本与读回原文。

### 前提纠正：驱动加载的是 regdb_xiaomi.bin，不是 regdb.bin
本机 `/vendor/firmware_mnt/image/peach/` 下**两个文件都存在且都是 24278 字节**：
`regdb.bin` md5 `f5c0dd69…`（= 我方 r1，头 `a2ce`），
`regdb_xiaomi.bin` md5 `bac61efe…`（= 我方 r2，头 `69e9`），两者相差 623 字节。
判定加载者的硬证据是内核模块里的字面量：

```
grep -aob 'regdb[_a-zA-Z0-9.]*' /vendor/lib/modules/icnss2.ko  →  43530:regdb_xiaomi.bin
grep -aob 'regdb[_a-zA-Z0-9.]*' /vendor/lib/modules/cnss2.ko   →  63451:regdb_xiaomi.bin
```

两个 ko 里**只有 `regdb_xiaomi.bin`，完全没有 `regdb.bin`**。上游 `icnss_qmi.c`
写的是 `#define REGDB_FILE_NAME "regdb.bin"`，说明小米在板级分支改了文件名。
→ **此前所有 bind 到 regdb.bin 的实验都打在未被加载的文件上**，属于无效实验。
common.sh 里"vendor 后缀优先"的注释方向正确，但其依据（logcat 原文）在本机
logcat/dmesg 中检索不到，应改以 ko 字符串为准。

### 实验一：加载文件里改 pair 选择子 → 活体表一字未变（否证"改 pair 即改表"）
脚本 `tools/regdb_work/net/s231.sh`（base64 下发，`setsid` 脱离会话，结果落
`/data/local/tmp/rB.txt`）。只改加载文件里 US 记录的 pair 低字节 `ea`→`e7`
（234 → 231 = APL17_ETSIC），偏移 3540 由 `recprobe.py` 离线算出并核对。

| 项 | 结果 |
| --- | --- |
| 补丁写入 | `od -j 3536 -N16` → `00 00 48 03 e7 00 21 55 53 …`（确认已改） |
| bind / 重载 | `BIND-OK`、挂载 1、`svc wifi disable/enable` 完成 |
| 活体表 | 仍是 `country US: DFS-FCC`，八行与基线逐行相同 |
| 预期新特征 | `ROW_2482=0`、`ROW_5650=0`、`ROW_36dBm=0`、`RADAR_ROWS=16` |

APL17_ETSIC 的特征一个都没出现 → **host 不使用记录里的 pair 字段**。

### 实验二：改 super6g 字节 → 6GHz 行也不变（否证 GhostUnlock 在本机的适用性）
`tools/regdb_work/net/s6.sh`：AR 记录（rec=0x0a0，offset 166）super6g
`0x05` → `0x21`（US 记录所用值，GhostUnlock 称其 live-safe）。rC.txt 结果：
6GHz 行仍是 AR 原有的 `(5925 - 7105 @ 320), (N/A, 24), NO-OUTDOOR`，
US 的 `(5945 - 7125 @ 160), 21, INDOOR` **完全没出现**（`ROW_7125=0`、`REG_21dBm=0`）。
→ 本机 super6g 同样不被采纳；GhostUnlock 的"只改 super6g 一字节即生效"
**不能推广到 peach_v2 / 本 HyperOS 组合**。

### 统一模型（本轮唯一存活结论）
**活体 iw 监管表 = host 编译期内置表按 alpha2 渲染；regdb 记录里的 pair 与
super6g 都不参与。** 该模型与两条否证一致，也与 host 源码一致
（`reg_db.c` 内没有任何 regdb.bin 解析器）。因此：
- 唯一的 2.4/5GHz 旋钮是**国家码本身**（`cmd wifi force-country-code`）；
- "新增/改写 00 记录"失去意义：alpha2=00 走的是退化 global 表
  （实测 `country 00: DFS-UNSET`，2.4G 20 dBm，无 6G），改记录字段不会改变渲染；
- regdb.bin 在 self-managed 路径上的实际作用仍未完全定性（固件仍需下载它，
  但本机 iw 表不由它决定）；"破解校验和以自定义监管表"这一目标已不再必要。

### 实测最优：AR 一个动作命中四条要求中的三条（零文件改动）
离线帕累托（`pareto.py`/`render.py`）先找到 `pair 231 = APL17_ETSIC`，
`alphamap.py` 显示真档里 **AR（阿根廷）** 已携带该 pair。实测
`cmd wifi force-country-code enabled AR` 与离线渲染**逐行一致**：

```
country AR: DFS-UNSET
  (2402 - 2482 @ 40),  (N/A, 30)      ← 2.4G 30 dBm，覆盖到 2482（US 只到 2472）
  (5170 - 5250 @ 80),  (N/A, 23)
  (5250 - 5330 @ 80),  (N/A, 36)      ← 高于 CN 的 33
  (5490 - 5590 @ 80),  (N/A, 36)
  (5650 - 5730 @ 80),  (N/A, 36)
  (5735 - 5835 @ 80),  (N/A, 36)
  (5925 - 7105 @ 320), (N/A, 24), NO-OUTDOOR
```

| 频段 | PHY 总数 | 启用 | DFS | NO-IR | 上限 |
| --- | --- | --- | --- | --- | --- |
| 2.4G | 14 | 13 | **0** | **0** | **30 dBm**（=US 且更宽） |
| 5G | 28 | 22 | **0** | **0** | **36 dBm**（>CN 33） |
| 6G | 60 | 58 | 0 | 0 | 24 dBm |

对照用户四条要求：功率上限优于 US/CN、去 DFS 与 NO-IR、6GHz 保留 → 三条达成。

### 国家码横向实测（同一方法逐个 force-country-code，无需 bind/重启）
`cmd wifi force-country-code enabled <CC>` 在 self-managed 路径上即时生效
（AR 实测 8 秒内读回即变），因此对比矩阵可低成本批量采集。注意：**批量循环里
个别国家码会连带触发驱动重载**，把设备 MCP 通道拖断，必须逐个执行。

| 国家码 | 管制域 | 2.4G 启用/上限 | 5G 启用/上限 | 6G 启用 | DFS 行 | NO-IR |
| --- | --- | --- | --- | --- | --- | --- |
| **AR** | DFS-UNSET | 13 / **30** | 22 / **36** | **58** | **0** | **0** |
| AU | DFS-ETSI | 13 / **36** | 22 / 36 | 24 | 13 | 0 |
| NZ | DFS-ETSI | 13 / **36** | 25 / 36 | 24 | 16 | 0 |
| US（基线） | DFS-FCC | 11 / 30 | 25 / 30 | 58 | 16 | 0 |

取舍：AU/NZ 把 2.4G 抬到 36 dBm，代价是 DFS 重新出现（13/16 行）且 6GHz 只剩
24 信道；**AR 是唯一"DFS=0 + NO-IR=0 + 6GHz 最多"的组合**，5G 高频 36 dBm
已与 AU/NZ 持平，2.4G 30 dBm 亦不低于 US。故按用户目标（去 DFS/NO-IR、
高功率、保 6GHz）选 **AR**。

### 源码侧 alpha2→pair 映射仍未锁定（诚实边界）
`reg_db.c` 里有 **4 份** `g_all_countries[]`（条件编译的不同数据库修订）：

```
@1229   206 条  AR->APL16_ETSIC   与实测吻合 0/3
@13083  207 条  AR->APL17_ETSIC   与实测吻合 1/3
@25047  207 条  AR->APL17_ETSIC   与实测吻合 1/3
@36997  207 条  AR->APL17_ETSIC   与实测吻合 1/3
```

（吻合度用三个已知实测点校验：AR→APL17_ETSIC、US→FCC15_FCCA、CN→APL14_CHNA。）
后三份都只匹配 1/3，US 的映射与实测不符 → **这份 LineageOS 源码不是本固件的
精确版本**，其 alpha2 表不能当权威。因此上表全部以**真机读回**为准，源码只用于
解释与离线预测（`render.py` 对 AR/US 的逐行预测已被实测证实）。

### 第四条"全信道 14/28/60"不可达，且与前三条互斥
- `14/28/60` 是 **PHY 总信道数**（上表"总数"列），任何国家都启不满；
  被 disabled 的信道（2484、5600/5620/5640、5845/5865/5885、5935、7115）
  恰好是渲染区间的**缝隙**，不是监管限制——`chancov.py` 离线复现了同一批缺口。
- 2.4G ch14 在全部内置表里**只由 MKKA 域提供**（`ch14tradeoff.py`：唯一命中
  `MKK5_MKKA` id=153），而它是 **23 dBm 且无 6GHz**。
- 因此 ch14 与"高功率 + 6GHz"互斥：AR = 13/22/58 @ 30/36/24，
  MKK5 = 14/12/0 @ 23/23/—。

### ch14 终局：连 MKKA 域也无法启用（已实测，非推断）
先误判过一次：`ch14tradeoff.py` 只扫真档记录，没扫 host 的 alpha2 表，
因此一度以为 MKK5_MKKA 没有国家码可达。源码里其实有：

```
CE(XA, MKK5_MKKA, 0, XA, 40, 160, 0, 0),      /* g_all_countries[]，后三份修订均有 */
{MKK5_MKKA, MKK5, MKKA},                      /* g_reg_dmn_pairs[] */
[MKKA] = {CTL_MKK, DFS_UNINIT_REGION, 0, 40, 0, 2, {CHAN_1_13_4, CHAN_14_1}},
[CHAN_14_1] = {2474, 2494, 20, 23, REGULATORY_CHAN_NO_OFDM},
```

实测 `cmd wifi force-country-code enabled XA`（XA 即小米 regdb 里自建的那个
alpha2，真档 pair=225，但 host 侧按自己的表渲染）：

```
country XA: DFS-UNSET
iw reg get : (2402 - 2482 @ 40), (N/A, 23)      ← 没有 2474-2494 那一行
iw phy     : * 2484.0 MHz [14] (disabled)        ← ch14 仍未启用
             2.4G 13 启用 @23 / 5G 20 @23 (DFS 16) / 6G 24 @23
```

功率 23 dBm、DFS-UNSET 说明 pair 确实是 MKK5 系，但 **host 没有把
`CHAN_14_1` 渲染进活体表**（2474-2494 整段缺席）。结合本节前文"这份源码不是
本固件的精确版本"，无论根因是版本差异还是 `NO_OFDM` 在 nl80211 侧被处理成
不发布该信道，结论都一样且可复现：
**在本机任何 alpha2 下 2.4G ch14 都不可启用**，"全信道 14" 这一条不是取舍问题，
而是硬不可达。同时 ko 与 vendor ini 里也没有任何 ch14/信道使能键
（只有 `gChannelBondingMode24GHz`、`gEnableVhtFor24GHzBand` 等带宽键），
驱动侧也没有绕过路径。

实验后设备已恢复 `country AR: DFS-UNSET`，phy#0 健康、102 MHz 行、挂载 0、
vendor 两文件 md5 仍为 `f5c0dd69…` / `bac61efe…`。

### 结论与后续选择
1. regdb 校验和之争到此为止：自定义监管表路线既不再必要，也不再可行
   （改字段无效，改 alpha2 才有效）。
2. 立即可用：`COUNTRY_PROFILE=CUSTOM` + `COUNTRY_CODE=AR`（v1.5 已支持 CUSTOM），
   实测得 2.4G 30 dBm / 5G 高频 36 dBm / 无 DFS 无 NO-IR / 6GHz 58 信道。
3. 若坚持 ch14：只能在 AR 与 MKKA(153) 间二选一，或验证 WCNSS/驱动侧是否有
   2.4G ch14 对应键（未验证）。
4. 若坚持"自定义 00"：需先证明 00 的渲染路径可读文件；已否证两条，
   不建议继续投入。

### 设备实验方法论（本轮踩坑，务必复用）
- 脚本下发用 **base64 单行**：`cat <<EOS` heredoc 在通道断开时会被截断，
  脚本没落地而实验静默失败（此前 resA.txt / respair.txt 缺失即此因）。
- 后台用 `setsid sh x.sh </dev/null >/dev/null 2>&1 &`；只写 `&` 会随会话结束被带走。
- `pkill -f <name>` 会匹配到自己的 shell 把自己杀掉（exit 137）；改用
  `for p in $(pgrep -f '/data/local/tmp/x.sh'); do kill -9 $p; done`。
- toybox `grep "MHz ["` 因方括号不平衡报错，必须加 `-F`。
- 多行 `python -c` 经 cmd 下发会丢输出：改写成 .py 文件再执行。
- 当前设备状态：vendor 两文件 md5 均为原始基线（`a2ce` / `69e9`），挂载 0，
  仅剩运行时 country override（AR），phy#0 健康、`iw phy` 102 行。
